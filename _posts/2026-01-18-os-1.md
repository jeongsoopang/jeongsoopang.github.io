## 1. Concept

A critical section (CS) is a region of code that accesses shared state and must not be executed by more than one thread or process at the same time.

The purpose of a critical section is to prevent race conditions, which are nondeterministic bugs caused by unsafe interleavings of reads and writes on shared data.

Typical symptoms of race conditions include:
- Lost updates, where one write overwrites another
- Reading inconsistent or partially updated state
- Bugs that disappear when logging, printing, or sleeping is added

---

## 2. The Critical Section Problem

A correct solution to the critical section problem must satisfy three properties, originally formalized by Dijkstra.

### Mutual Exclusion
At most one thread or process may execute inside the critical section at any time.

### Progress
If no thread is currently in the critical section, one of the threads that wishes to enter must eventually be allowed to do so.

### Bounded Waiting
After a thread requests entry to the critical section, there exists a finite bound on the number of times other threads may enter before that thread is granted access.

These conditions rule out both deadlock and starvation.

---

## 3. Structure of Concurrent Code

Concurrent programs that protect shared data typically follow a four-part structure:

```text
Entry Section -> Critical Section -> Exit Section -> Remainder Section
 (acquire)        (shared state)      (release)      (private work)
```

- Entry section: protocol to acquire access (lock, flag, atomic check)
- Critical section: code that reads or modifies shared data
- Exit section: releases ownership or clears state
- Remainder section: code that does not access shared resources

## 4. Software-Only Algorithms

Early solutions to the critical section problem rely purely on shared memory and busy waiting, without hardware support.  
These algorithms assume sequential consistency and are mainly used for understanding correctness properties such as progress and bounded waiting.

They are not practical on modern systems but remain important conceptually.

### Peterson’s Algorithm (Two Threads)

```c
// Shared variables
volatile bool want[2] = {false, false};
volatile int turn = 0;

// Thread i (i = 0 or 1)
want[i] = true;
turn = 1 - i;
while (want[1 - i] && turn == 1 - i) {
  // busy wait
}

// critical section

want[i] = false;
```

Peterson’s algorithm satisfies:

- mutual exclusion
- progress
- bounded waiting

This holds only under a sequentially consistent memory model.
Modern CPUs and compilers may reorder operations, so real implementations require memory barriers and atomic semantics.

## 5. Hardware Support: Atomic Operations

Modern operating systems rely on hardware-provided atomic instructions to implement correct and efficient synchronization.  
These instructions guarantee that a read-modify-write sequence occurs atomically, without interference from other processors.

Atomic operations form the foundation of most lock implementations.

### Common Atomic Primitives

Test-and-Set (TAS):

```c
bool test_and_set(bool *x) {
  bool old = *x;
  *x = true;
  return old;
}
```

Compare-and-Swap (CAS):

```c
CAS(addr, expected, new):
  if (*addr == expected) {
    *addr = new;
    return true;
  } else {
    return false;
  }
```

Other common primitives include:

- fetch-and-add
- exchange (XCHG)
- load-linked / store-conditional (LL/SC)

These primitives allow synchronization algorithms to be implemented without disabling interrupts.

### Memory Ordering

Most modern CPUs do not provide sequential consistency by default.
As a result, correct synchronization requires explicit memory ordering guarantees.

Key concepts:

- acquire semantics when acquiring a lock
- release semantics when releasing a lock
- fences or barriers when stronger ordering is required

In C/C++, these guarantees are expressed using atomic operations with acquire and release memory orders.

## 6. Locks and Locking Primitives
### 6.1 Spinlocks

Spinlocks repeatedly check a lock variable until it becomes available.

```c
std::atomic<bool> locked{false};

void lock() {
  while (locked.exchange(true, std::memory_order_acquire)) {
    // busy wait
  }
}

void unlock() {
  locked.store(false, std::memory_order_release);
}
```

Spinlocks are appropriate only when:

- the critical section is very short
- threads are running on different CPUs
- blocking or sleeping is not allowed

Holding a spinlock for too long wastes CPU cycles.

### 6.2 Mutexes

Mutexes allow threads to sleep when the lock is unavailable.

```c
pthread_mutex_lock(&m);
/* critical section */
pthread_mutex_unlock(&m);
```

They are preferred when:

- the critical section may be long
- blocking operations may occur inside the CS

Most implementations optimize the uncontended case to avoid entering the kernel, often using futex-based designs.

### 6.3 Reader–Writer Locks

Reader–writer locks allow:

- multiple readers to enter the critical section concurrently
- writers to have exclusive access

Policy variants include:

- reader-preferred
- writer-preferred
- fair

Improper policy choice may result in starvation.

## 7. Higher-Level Synchronization
### 7.1 Semaphores

A semaphore maintains a non-negative integer value accessed via wait and signal operations.

Counting semaphores are commonly used for resource management and producer–consumer problems.

```c
wait(empty);
wait(mutex);
produce();
signal(mutex);
signal(full);
```

Binary semaphores resemble mutexes but do not enforce ownership semantics.

### 7.2 Monitors and Condition Variables

Monitors provide mutual exclusion automatically at the language or runtime level.

Condition variables allow threads to wait for a condition while atomically releasing the associated lock.

Key rules:

- always wait inside a loop
- recheck the condition after waking
- signaling does not immediately transfer control

This behavior follows Mesa semantics.

## 8. Kernel Space vs User Space

| Aspect | User Space | Kernel Space |
|------|-----------|--------------|
| Typical primitives | pthread mutexes, RW locks, semaphores | spinlocks, mutexes, RCU |
| Blocking behavior | sleeps via futex | kernel-managed wait queues |
| Interrupt control | not allowed | possible for short sections |
| Sleeping in CS | allowed with mutex | forbidden with spinlocks |
| Priority inversion | PI mutexes | kernel PI/PCP mechanisms |

User-space synchronization is optimized to avoid system calls on the fast path.

## 9. Worked Examples

### 9.1 Protecting a Shared Counter

Incorrect:

```c
i++;
```

Correct using a mutex:

```c
pthread_mutex_lock(&m);
i++;
pthread_mutex_unlock(&m);
```

Correct using atomics:

```c
i.fetch_add(1, std::memory_order_relaxed);
```

Stronger ordering may be required when additional invariants are involved.

### 9.2 Producer–Consumer with Condition Variables
```c
while (queue.full())
  pthread_cond_wait(&not_full, &m);

while (queue.empty())
  pthread_cond_wait(&not_empty, &m);
```

Waiting must always be guarded by a condition check.

### 10. Quick Selection Guide

| Scenario | Recommended Primitive |
|--------|----------------------|
| very short critical section on multicore | spinlock |
| long or blocking critical section | mutex |
| many readers, few writers | reader–writer lock |
| fixed-size pool of resources | counting semaphore |
| waiting for a condition to become true | mutex + condition variable |
| avoid busy waiting | sleeping locks (mutex, semaphore) |
| real-time or priority-sensitive threads | priority-inheritance mutex |
