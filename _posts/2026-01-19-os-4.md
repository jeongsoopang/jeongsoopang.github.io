## 1) Scheduler’s Role

- Multiple processes compete for CPU time
- When more than one process is **Ready**, the scheduler chooses which runs next
- Scheduling strongly affects perceived system performance

Scheduling decisions typically occur when:
- A process is created
- A process exits or blocks
- An I/O completion interrupt occurs

---

## 2) Context Switch Overhead

Switching the CPU from one process to another is not free.

Typical steps:
- Trap into kernel mode
- Save current process state (registers, PC, memory mapping)
- Select the next process
- Restore its state
- Resume execution

Excessive context switching wastes CPU time and degrades performance.

---

## 3) Process CPU Behavior

Processes generally fall into two categories:

| Type        | Behavior           | Resource Usage | Notes |
|------------|--------------------|----------------|------|
| CPU-bound  | Long CPU bursts    | Mostly CPU     | Few I/O operations |
| I/O-bound  | Short CPU bursts   | Mostly I/O     | Frequently blocked |

> As CPUs become faster, modern workloads tend to be more I/O-bound.

---

## 4) Preemptive vs Non-Preemptive Scheduling

| Strategy        | CPU Released When…                         | Advantages                     | Drawbacks |
|-----------------|--------------------------------------------|--------------------------------|-----------|
| Preemptive      | Time quantum expires or higher priority arrives | Good responsiveness, fairness | More context switch overhead |
| Non-preemptive  | Process blocks or exits                    | Simple, low overhead           | Poor response for long jobs |

Preemption requires hardware timer interrupts and kernel support.

---

## 5) Scheduling Goals

| System Type     | Primary Metrics |
|-----------------|-----------------|
| All systems     | Fairness, CPU utilization, policy enforcement |
| Interactive     | Response time, proportionality |
| Batch           | Throughput ↑, turnaround time ↓ |
| Real-time       | Deadline guarantees, predictability |

---

## 6) Common Scheduling Algorithms

### 6.1 First-Come First-Served (FCFS)

- Non-preemptive
- Simple FIFO ordering

Problem:
- Convoy effect: long jobs delay short ones

---

### 6.2 Shortest Job First (SJF)

- Non-preemptive
- Minimizes average turnaround time
- Requires knowing job length in advance

Limitations:
- Unrealistic in practice
- Long jobs may starve

---

### 6.3 Round Robin (RR)

- Preemptive
- Each process gets a fixed time quantum

Trade-off:
- Quantum too small → high overhead
- Quantum too large → behaves like FCFS

Commonly used in interactive systems.

---

### 6.4 Priority Scheduling

- Highest-priority process runs first
- Often combined with Round Robin within priority classes

Problem:
- Starvation of low-priority processes

Solution:
- Aging (gradually increase priority over time)

---

### 6.5 Lottery Scheduling

- Each process holds lottery tickets
- Scheduler randomly selects a ticket holder

Advantages:
- Flexible priority control
- Weighted fairness

---

### 6.6 Earliest Deadline First (EDF)

- Real-time scheduling
- Task with the closest deadline runs first

Requirement:
- Processes must declare deadlines in advance

---

## 7) Policy vs Mechanism

- Scheduling mechanism: how scheduling is implemented
- Scheduling policy: rules deciding who runs and when

Separating policy from mechanism allows flexibility.
For example, parent processes may assign priorities to children.

---

## 8) Scheduling Threads

Scheduling depends on thread implementation:

- User-level threads  
  - Kernel is unaware of threads  
  - Scheduling handled in user space  

- Kernel-level threads  
  - Kernel schedules individual threads  
  - True parallelism on multicore systems  

The choice determines possible execution interleavings.

## 9) Dining Philosophers Problem

A classic synchronization problem illustrating deadlock and starvation.

![Dining Philosopher](../images/dining_1.jpg){ width="500" }

- Five philosophers share chopsticks
- Each philosopher needs two chopsticks to eat

![Solution](../images/dining_2.jpg){ width="500" }

---

### 9.1 Problem Recap

- Deadlock: all philosophers pick one chopstick and wait forever
- Starvation: a philosopher may never eat
- Safety: adjacent philosophers must not eat simultaneously

---

### 9.2 Key Data Structures

| Component | Purpose |
|---------|---------|
| `state[i]` | THINKING / HUNGRY / EATING |
| `mut` | Mutex protecting shared state |
| `s[i]` | Semaphore per philosopher |
| `test(i)` | Determines if philosopher `i` may eat |

---

### 9.3 Execution Flow

#### When a philosopher becomes hungry (`take_cs(i)`)

1. Lock mutex
2. Set state to `HUNGRY`
3. Call `test(i)`
4. Unlock mutex
5. Block on `s[i]` if chopsticks unavailable

#### After eating (`put_cs(i)`)

1. Lock mutex
2. Set state to `THINKING`
3. Test neighbors (`LEFT`, `RIGHT`)
4. Unlock mutex

---

### 9.4 Core Logic: `test(i)`

```c
if (state[i] == HUNGRY &&
    state[LEFT] != EATING &&
    state[RIGHT] != EATING) {
    state[i] = EATING;
    up(&s[i]);
}
```
This ensures a philosopher eats only when both neighbors are not eating.

---

## 9.5 How the Solution Addresses the Classical Problems

| Problem | Explanation |
|-------|-------------|
| Deadlock | Circular wait is eliminated. A philosopher is allowed to eat only when both neighboring philosophers are not eating. No philosopher holds one chopstick while waiting indefinitely for the other. |
| Starvation | When a philosopher finishes eating, both neighbors are immediately tested and may be signaled. This ensures that hungry philosophers eventually get a chance to eat. |
| Race Conditions | All accesses and updates to shared state (`state[]`) are protected by a mutex, preventing concurrent inconsistent updates. |
| Neighbor Conflicts | The `test(i)` function explicitly checks the left and right neighbors’ states, guaranteeing that adjacent philosophers never eat simultaneously. |

### Key Insight

The combination of:
- a global mutex for state protection, and
- per-philosopher semaphores for permission to eat

ensures mutual exclusion, progress, and bounded waiting, while avoiding deadlock and starvation.
