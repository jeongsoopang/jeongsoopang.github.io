## Interprocess Communication (IPC) & Synchronization

Interprocess Communication (IPC) and synchronization mechanisms are fundamental to coordinating concurrent processes and threads that access shared state.  
Their primary purpose is to **prevent race conditions** while guaranteeing both **correctness** and **liveness**.

A race condition occurs when program behavior depends on the timing or interleaving of concurrent operations on shared data.

---

## 1) Correctness Properties (Dijkstra)

A correct synchronization solution must satisfy the following properties:

1. **Mutual Exclusion**  
   At most one thread or process may execute within the critical section at any time.

2. **Progress**  
   If no thread is inside the critical section, one of the waiting threads must eventually be allowed to enter.

3. **Bounded Waiting (No Starvation)**  
   A thread requesting entry into the critical section must not wait indefinitely.

These properties distinguish safe synchronization from merely functional concurrency.

---

## 2) Critical Section Pattern

### Structure

```text
entry_section();        // acquire permission
/* critical section */  // access shared data
exit_section();         // release permission
remainder_section();    // independent work
```

### Implementation Approaches

Software-only algorithms
: Strict alternation, Peterson’s algorithm (two threads), Bakery algorithm (N threads)

Hardware-supported primitives
: Atomic instructions such as Test-and-Set, Compare-and-Swap, Fetch-and-Add

OS-level primitives
: Mutexes, semaphores, condition variables, monitors

## 3) Mutexes and Condition Variables
### Mutex

A mutex ensures exclusive access to a critical section.

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

pthread_mutex_lock(&m);
/* critical section */
pthread_mutex_unlock(&m);
```

### Condition Variable

Condition variables allow threads to wait for a condition while releasing the mutex atomically.

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  cv = PTHREAD_COND_INITIALIZER;
int ready = 0;

void wait_until_ready() {
    pthread_mutex_lock(&m);
    while (!ready)
        pthread_cond_wait(&cv, &m);
    pthread_mutex_unlock(&m);
}

void signal_ready() {
    pthread_mutex_lock(&m);
    ready = 1;
    pthread_cond_signal(&cv);
    pthread_mutex_unlock(&m);
}
```

The predicate must always be checked in a while loop to guard against spurious wakeups.

## 4) Semaphores

A semaphore is an integer-valued synchronization primitive accessed through two atomic operations:

wait() / P() / down() — decrement and block if negative

signal() / V() / up() — increment and wake waiting threads if needed

### Binary Semaphore as a Mutex
```c
sem_t s;
sem_init(&s, 0, 1);

sem_wait(&s);
/* critical section */
sem_post(&s);
```
### Producer–Consumer (Bounded Buffer)
```c
#define N ...
item_t buf[N];
int in = 0, out = 0;

sem_t empty, full, mutex;

void producer(item_t x) {
    sem_wait(&empty);
    sem_wait(&mutex);
    buf[in] = x;
    in = (in + 1) % N;
    sem_post(&mutex);
    sem_post(&full);
}

item_t consumer() {
    item_t x;
    sem_wait(&full);
    sem_wait(&mutex);
    x = buf[out];
    out = (out + 1) % N;
    sem_post(&mutex);
    sem_post(&empty);
    return x;
}
```

## 5) Monitors

A monitor encapsulates shared data together with synchronization logic.

- Only one thread executes monitor procedures at a time
- Condition variables are used internally for waiting and signaling

```c
monitor BoundedBuffer {
    condition not_full, not_empty;
    item_t buf[N];
    int in = 0, out = 0, cnt = 0;

    procedure put(x) {
        while (cnt == N) wait(not_full);
        buf[in] = x;
        in = (in + 1) % N;
        cnt++;
        signal(not_empty);
    }

    procedure get(out_x) {
        while (cnt == 0) wait(not_empty);
        out_x = buf[out];
        out = (out + 1) % N;
        cnt--;
        signal(not_full);
    }
}
```

## 6) Deadlock

Deadlock is a situation where a set of processes or threads are permanently blocked, each waiting for resources held by others.

### Coffman Conditions

Deadlock can occur **if and only if** all four conditions hold simultaneously:

1. **Mutual Exclusion**  
   Some resources cannot be shared and must be held exclusively.

2. **Hold and Wait**  
   A process holds at least one resource while waiting to acquire additional resources.

3. **No Preemption**  
   Resources cannot be forcibly taken; they must be released voluntarily.

4. **Circular Wait**  
   A circular chain exists where each process waits for a resource held by the next.

---

### Deadlock Prevention

Prevent deadlock by breaking at least one Coffman condition:

- **Eliminate Hold-and-Wait**  
  Require processes to request all resources at once.  
  (Low utilization, possible starvation.)

- **Allow Preemption**  
  Force a process to release resources if it cannot obtain all required ones.

- **Resource Ordering**  
  Impose a global order on resource acquisition; processes must request resources in ascending order.

---

### Deadlock Avoidance (Banker’s Algorithm)

- The system grants a resource request **only if** it remains in a safe state.
- A safe state means there exists some sequence in which all processes can complete.
- Requires each process to declare its **maximum resource requirements** in advance.

---

### Deadlock Detection and Recovery

- **Detection**  
  Build a wait-for graph (WFG); a cycle indicates deadlock.

- **Recovery**  
  Abort or roll back selected processes to reclaim resources.

## 7) Performance Considerations

| Aspect | Guidance |
|------|----------|
| Busy waiting | Spin only for very short waits; otherwise block |
| Lock granularity | Coarse locks simplify design; fine-grained locks increase concurrency |
| Contention | Minimize critical sections; partition shared data |
| False sharing | Pad frequently written data to cache-line size |
| Lock-free design | Use CAS with care; handle ABA and memory reclamation |

---

## 8) Memory Ordering

Modern CPUs and compilers may reorder memory operations.

- Synchronization primitives establish **happens-before** relationships.
- Mutex lock/unlock pairs imply acquire–release semantics.
- Lock-free algorithms require explicit memory ordering using atomic operations and fences.

Correct memory ordering is essential for correctness on weakly ordered architectures.

## Key Terms

| Term | Meaning |
|------|--------|
| Mutual exclusion | Only one thread may enter a critical section |
| Semaphore | Counting synchronization primitive |
| Mutex | Binary lock for exclusive access |
| Condition variable | Predicate-based waiting mechanism |
| Monitor | Encapsulated synchronization abstraction |
| Deadlock | Circular waiting on resources |
| Starvation | A thread never makes progress |
| Spinlock | Busy-wait lock for short critical sections |

---

## Summary

Interprocess communication and synchronization primitives ensure safe and efficient concurrency.

A correct design must guarantee:
- **Safety**: shared data is never corrupted
- **Liveness**: threads eventually make progress

Choosing the right primitive requires balancing correctness, performance, fairness, and implementation complexity.
