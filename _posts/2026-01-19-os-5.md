## 1) What Is a Deadlock?

A **deadlock** occurs when a set of processes are blocked forever,  
each waiting for a resource that is held by another process in the same set.

No process can proceed, and the system makes no progress.

---

## 1.1 Four Necessary Conditions (Coffman’s Conditions)

A deadlock can occur **if and only if** all four conditions hold simultaneously:

| Condition | Description |
|---------|-------------|
| **Mutual Exclusion** | At least one resource is held by only one process at a time |
| **Hold and Wait** | A process holds one resource while waiting for another |
| **No Preemption** | Resources cannot be forcibly taken away |
| **Circular Wait** | A circular chain of processes exists |

If **any one condition is broken**, deadlock is impossible.

---

## 2) Resource Types

| Resource Type | Characteristics | Examples |
|--------------|-----------------|----------|
| **Preemptable** | Can be safely taken away | CPU, memory pages |
| **Non-preemptable** | Cannot be taken without failure | Printer, tape drive |

Deadlocks typically involve **non-preemptable resources**.

---

## 3) Resource Allocation Graph (RAG)

Graph representation of resource usage:

- **Process → Resource** : request edge  
- **Resource → Process** : assignment edge  

### Deadlock Rule
- If each resource has **one instance**:
  - **Cycle exists → Deadlock**
- If resources have **multiple instances**:
  - Cycle **may or may not** indicate deadlock

**Example cycle:**

```text
P1 → R1 → P2 → R2 → P1
```


---

## 4) Deadlock Detection Example

Assume the following state:

- Process **D** holds **U**, requests **S, T**
- Process **E** holds **T**, requests **V**
- Process **G** holds **V**, requests **U**

### Cycle Detected
```text
U → D → T → E → V → G → U
```


**Deadlock exists among processes D, E, and G.**

---

## 5) Ostrich Algorithm

> “If deadlock happens rarely, ignore it.”

- Used in **UNIX / Linux**
- Deadlock handling is expensive
- Acceptable if:
  - Deadlocks are rare
  - Recovery cost > ignoring cost

A **pragmatic engineering choice**, not a theoretical solution.

---

## 6) Deadlock Detection (Multiple Resource Instances)

Uses matrix-based detection:

| Symbol | Meaning |
|------|---------|
| **E** | Existing resources |
| **A** | Available resources |
| **C** | Current allocation |
| **R** | Remaining requests (Need) |

### Detection Principle
If no process can satisfy `R[i] ≤ A`  
and the situation does not change → **Deadlock exists**

---

## 7) Deadlock Recovery

Once deadlock is detected:

| Method | Description | Drawback |
|------|-------------|----------|
| **Preemption** | Take resources from processes | Data corruption risk |
| **Process Termination** | Kill one or more processes | Lose progress |
| **Rollback** | Restore from checkpoints | High overhead |

Recovery is **disruptive and costly**.

---

## 8) Deadlock Avoidance

Avoidance ensures the system **never enters a deadlock-prone state**.

---

## 8.1 Safe vs Unsafe State

| State | Meaning |
|------|---------|
| **Safe** | There exists an execution order where all processes finish |
| **Unsafe** | No guaranteed completion order |

> Unsafe ≠ Deadlock  
> But unsafe states may **lead** to deadlock.

---

## 8.2 Banker’s Algorithm

Avoids unsafe states by **simulating resource allocation** before granting a request.

### Requirements
- Each process declares **maximum resource needs**
- System checks safety before allocation

---

### 8.2.1 Banker’s Decision Rule

1. Check `Request ≤ Available`
2. Pretend to allocate resources
3. Run **Safety Algorithm**
4. If state is safe → grant  
   Else → deny request

---

## 8.3 Safety Test Example

**Resource Types:** Scanners, Plotters, Printers, DVD  
**Total Resources:**  
E = (6, 3, 4, 2)

**Available:**  
A = (1, 1, 2, 0)

### Allocation Matrix (C)

| Process | Allocation |
|-------|------------|
| P1 | (3,0,1,1) |
| P2 | (0,1,0,0) |
| P3 | (1,0,1,0) |
| P4 | (1,1,0,1) |
| P5 | (0,0,0,0) |

### Need Matrix (R)

| Process | Need |
|-------|------|
| P1 | (2,1,0,0) |
| P2 | (0,1,1,1) |
| P3 | (3,1,0,0) |
| P4 | (0,0,1,0) |
| P5 | (3,1,1,0) |

---

### Safety Sequence

1. A=(1,1,2,0) → **P4** runs → A=(2,2,2,1)
2. **P2** runs → A=(2,3,2,1)
3. **P1** runs → A=(5,3,3,2)
4. **P3** runs → A=(6,3,4,2)
5. **P5** runs

**Safe sequence:**  
**P4 → P2 → P1 → P3 → P5**

✔ System is in a **SAFE state**

---

## 9) Deadlock Prevention

Prevent deadlock by **breaking one of the four conditions**:

| Broken Condition | Strategy | Practical |
|-----------------|----------|----------|
| Mutual Exclusion | Make resources sharable | ✗ |
| Hold & Wait | Request all at once | ✗ |
| No Preemption | Force resource release | ✗ |
| Circular Wait | Impose resource ordering | ✓ |

### Most Practical Solution
➡ **Eliminate circular wait by resource ordering**

---

### Key Takeaway

Deadlock handling strategies trade off:

- **Performance**
- **Complexity**
- **System safety**

Real systems often combine:
- Ostrich approach
- Limited detection
- Careful resource ordering
